# 语音输入与文字意图识别设计方案

本文分为两个独立部分：第一部分负责语音转文字，第二部分负责用户确认发送后的文字分类和回答。第二部分已接入代码；业务查询仅预留接口，尚未连接业务数据库。第一部分较早的交互描述以现有“输入框实时出字、暂停/继续、对勾结束”代码为准。

## 第一部分：语音输入 ASR

### 1. 目标与范围

在两个输入框中增加语音输入：

- 主网页：Vue 3 页面。
- 悬浮窗：现有 `/emb` 原生 HTML/JavaScript 页面。

首版定位为可现场展示的 Demo：真实调用阿里云识别，不用预设文字或假波形替代。已确认桌面 Chrome / Edge、普通话、允许音频上传阿里云、匿名访问、单次录音最长 60 秒；不增加静音自动停止。本轮只完善文档，不接入真实账号、不调用收费接口、不修改应用代码。

用户点击麦克风后展开语音面板，连接就绪并正式开始录音后，上方实时展示识别文字、下方展示音量波形；用户点击右侧对勾结束录音，等待最终文字回填原输入框，检查、修改后点击原有发送按钮。语音识别阶段不自动发送问题，也不执行文档查询、数据库查询或 Agent 判断。

本部分只解决：

```text
麦克风采集 → 实时 ASR → 面板上方实时展示文字 → 对勾结束识别 → 回填输入框 → 用户确认发送
```

本部分不涉及：

- 用户登录、角色权限和复杂鉴权。
- HTTP/HTTPS 证书申请和部署细节；浏览器使用麦克风的必要前提仍需满足，见第 5 节。
- 文字意图识别与分流，单独在第二部分设计。
- TTS、录音文件保存和语音历史记录。
- 高并发、多实例部署、自动重连续录、多语种切换、热词平台等生产级扩展。

### 2. 整体架构

```text
主网页 / 悬浮窗
  麦克风
    ↓
  浏览器录音与音频转换
    ↓  自有 WebSocket：上传音频、接收识别文字
Spring Boot 后端
    ↓
  官方 DashScope Java SDK
    ↓
阿里云 Qwen-Audio-ASR-Message
    ↑
  中间结果、最终结果
    ↑
Spring Boot 后端通过自有 WebSocket 返回
    ↑
语音面板上方实时展示文字
    ↓
点击对勾结束识别，最终文字回填输入框
    ↓
用户检查、编辑并点击发送，调用原有文字问答接口
```

这是一次语音识别，但包含两段通信：

1. **浏览器 ↔ Spring Boot：自有 WebSocket**
   - 接收浏览器上传的音频。
   - 把中间识别结果和最终识别结果返回给浏览器。
   - 由我们定义消息格式和连接生命周期。

2. **Spring Boot ↔ 阿里云：官方 Java SDK**
   - 后端使用 `com.alibaba:dashscope-sdk-java` 调用阿里云 ASR。
   - 模型使用 `qwen-audio-3.1-asr-flash-message`，API Key 仅保留在后端。
   - SDK 负责阿里云侧的连接、任务指令、音频发送和结果回调。
   - 不在后端重复手写阿里云原生 WebSocket 协议。

因此，两个 WebSocket/SDK 不是重复识别：

```text
浏览器 WebSocket：解决“浏览器如何和我们的后端通信”
Java SDK：解决“后端如何调用阿里云 ASR”
阿里云 ASR：真正执行声音转文字
```

#### 2.1 阿里云接入参数

按 2026-11-11 核对的官方文档，本项目首版采用：

| 配置 | 约定 |
| --- | --- |
| 模型 | `qwen-audio-3.1-asr-flash-message`，不是录音文件识别或 TTS 模型 |
| 地域 | 华北 2（北京），作为湖北使用场景的大陆接入基线；不承诺仅凭用户所在地即可判断实际最低延迟 |
| 上游地址 | `wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference` |
| 凭证 | 北京地域可调用该模型的 API Key，存入服务端环境变量 `DASHSCOPE_API_KEY`；Workspace ID 与端点一并配置 |
| 音频 | `format=pcm`、`sample_rate=16000`；浏览器实际输出单声道、有符号 16bit 小端 PCM，无 WAV 文件头 |
| 实时结果 | `intermediate_result_enabled=true`，否则默认只返回句子最终结果，无法满足实时出字 |
| 语言 | `language_hints=["zh"]`、`keep_dialect=false`，按普通话转写 |
| 文本处理 | `disfluency_removal_enabled=false`，首版不主动润色用户问题 |
| 静音保活 | `heartbeat=true`，并持续发送真实采集的静音帧；不能因静音而停止发音频 |
| 断句 | `max_sentence_silence=800`，先用默认值；这是句子结束阈值，不是结束整次录音 |
| VAD | 首版保持默认 `far_field_meeting_16k`，实际设备效果不好再测试近场选项，不先调噪音阈值 |

端点、API Key 和业务空间必须匹配；不能把现有文字模型的 HTTP 地址直接当成 ASR 地址。ASR 端点和模型单独配置，不覆盖现有 Spring AI 文字模型配置。

首版不上传历史对话或整份政策文档来辅助识别，也不接热词库；后续确有专有名词误识别，再按实际词表启用热词，不影响本次主流程。这里的“不润色”不代表识别绝对准确，最终文字仍需用户检查。


```text
com.alibaba:dashscope-sdk-java
```

#### 3.1 SDK 的使用边界与 ready

- 使用双向流式识别，不使用“录完上传文件、等一次完整结果”的调用方式。
- 官网麦克风示例中的 `javax.sound.sampled` 采集的是运行 Java 的电脑/服务器，不是浏览器。这里只参考 SDK 的参数、发送及回调；用户声音必须来自浏览器上传。
- 官方 `Recognition` 高层回调只有 `onEvent/onComplete/onError`，没有 `onOpen`。调用 `call()` 返回、浏览器 WebSocket 打开，都不能直接证明云端任务已经可接收音频。
- 为严格满足“云端就绪后才录音”，`DashScopeAsrProvider` 使用 SDK 可透传启动事件的底层双向流接口，启用 `passTaskStarted=true`，确认收到 `task-started` 后再向浏览器发送自有 `ready`。参数和音频流使用 SDK 承载，结束输入流由 SDK 发送结束指令。
- 结束判断必须先验证：高层结果可能裁剪原始事件头，SDK 的任务结束与部分关闭路径也可能都触发 `onComplete`。不能假定 `getEvent()` 总能返回 `task-finished`，或仅凭 `onComplete` 判断成功。
- Demo 的第一步先验证 SDK 的启动、正常结束、异常关闭和取消映射；需要时只在 Provider 内增加 SDK 事件监听适配，不把 SDK 内部类和原始事件判断散落到业务代码中。任务启动前失败不进入录音态，未确认正常结束则按失败保留已确认文字，不能伪装完整成功。
- 这是同一份 Java SDK 的适配，不另写阿里云 WebSocket 客户端、不再同时创建第二个 `Recognition` 任务，也不反射或修改 SDK 私有字段。若锁定版本不能满足事件映射，应先说明问题再调整接入方式，不用固定延时或空白音频冒充 ready。
- 若使用高层 `Recognition.stop()`，它会等待回调而阻塞；不能放在 SDK 回调线程或浏览器消息接收线程里执行。本方案将 Provider 的收尾封装为异步操作。

### 4. 一次完整识别流程

#### 4.1 点击开始

1. 用户点击网页或悬浮窗中的麦克风按钮，展开语音面板；原问答正在生成时禁用麦克风，不能开启录音。
2. 前端保存输入框当前文字、光标位置和选区，初始化音频处理并请求浏览器麦克风权限；等待授权时展示对应状态，不显示“正在录音”。应在点击交互中创建/恢复 `AudioContext`，避免等异步连接结束才恢复导致无法启动。
3. 权限通过后进入连接状态：波形位置显示加载动画，辅以轻量的“连接中…”；尚未正式录音，不展示动态录音波形，也不开始计时。
4. 前端连接后端语音 WebSocket `/api/v1/speech/recognize`，发送 `start` 指令和 `recordingId`。
5. 后端创建本次 `SpeechSession`，使用 Java SDK 创建阿里云识别任务；等待真实 `task-started`，而不是按固定延时推测连接成功。
6. 后端返回 `ready` 后，前端正式开始录音和发送音频，加载动画切换为随实际音量变化的波形，并显示录音计时；不额外显示“请开始说话”。权限通过后浏览器可能已显示设备占用标识，但 ready 前音频不得缓存回传或计入本次录音。

如果权限被拒绝、连接失败或 ASR 任务创建失败，输入框原文字保持不变，恢复普通文字输入。

单次录音最长 60 秒，从正式开始录音计算，不包含授权和连接时间；前端按实际采集开始计时，后端从收到首个有效音频帧计时并核对音频字节量，正常只相差约一帧的传输时间。达到上限后自动进入结束识别流程，不自动发送问题。首版不增加静音自动停止，用户停顿思考时仍可继续录音，直至点击对勾或达到时长上限。

#### 4.2 采集和发送音频

浏览器通过 `getUserMedia` 获取麦克风音频，再用 `AudioWorklet` 处理成统一格式，通过 WebSocket 分段发送：

```text
16kHz
单声道
16bit
小端
PCM
```

这些参数的含义：

- `16kHz`：每秒采样 16000 次。
- `单声道`：只保留一路声音。
- `16bit`：每个采样点使用 2 字节记录。
- `小端`：多字节数据的排列方式，由程序处理。
- `PCM`：未压缩的原始采样数据。

浏览器实际采样率可能不是 16kHz，因此必须进行真实重采样，不能只填写一个 `sampleRate: 16000`。不能把 `MediaRecorder` 产生的 WebM/Opus 文件块直接当作 PCM 上传。

建议每约 100ms 发送一个音频帧，避免一次积累过多音频，也避免发送过于零散的数据。

按本方案每帧约 3200 字节，每秒 32000 字节，60 秒约 1.92 MB。最后一帧允许不足 100ms，但必须是完整的 16bit 采样点；直接发送二进制，不加 Base64、JSON 音频封装或 WAV 文件头。

重采样器要保留跨帧状态并做必要的抗混叠处理，不逐帧随意抽点；PCM 写入需显式指定小端。只处理声音，不把麦克风接到扬声器播放。静音时仍按同样节奏发帧；网页切到后台导致采集中断时，不伪造静音掩盖故障。

#### 4.3 后端转发到阿里云

后端收到浏览器的二进制音频后，通过 Java SDK 发送给阿里云 ASR：

```text
浏览器音频帧
  → Spring WebSocket Handler
  → SpeechSession
  → DashScope Java SDK
  → 阿里云 ASR
```

后端需要维护浏览器连接和阿里云识别任务的一一对应关系，不能把不同用户或不同录音的音频混在一起。

每条连接只承载一次录音，不复用到下一次；音频帧与 `stop` 必须串行处理，先复制浏览器帧中需要保留的字节，再交给异步队列，避免缓冲区复用。后端收到超规格音频或队列积压时明确报错，不悄悄丢帧后继续展示不完整结果。

#### 4.4 实时返回文字

阿里云返回识别结果后，Java SDK 通过回调交给后端；后端统一转换为自己的消息格式，再通过浏览器 WebSocket 返回：

```text
阿里云 ASR
  → Java SDK 回调
  → Spring Boot 统一结果
  → 浏览器 WebSocket
  → 语音面板上方的文字区
```

SDK 返回的阿里云事件与自有事件区分如下：

| 阿里云事件 / 字段 | 自有事件 | 用途 |
| --- | --- | --- |
| `task-started` | `ready` | 云端任务已准备好，可开始采集和发送 |
| `result-generated` 且 `sentence_end=false` | `partial` | 当前句子的临时结果，可能修正 |
| `result-generated` 且 `sentence_end=true` | `final` | 当前句子的最终结果，不代表整次录音结束 |
| `task-finished`，正常结束确认 | `complete` | 整次识别完成，携带本次已确认全文 |
| `task-failed` / 网络、SDK 异常 | `error` | 识别失败，不映射为正常完成 |

若结果带 `heartbeat=true` 或只是空的句首事件，不当作识别文字。后端以阿里云 `sentence_id` 映射自有 `segmentId`，自行生成该句递增的 `revision`；`recordingId/revision` 是本系统字段，不能误认为厂商原样返回的字段。

录音期间，识别文字统一展示在语音面板上方；尚无结果时留空，不添加“请开始说话”等占位提示。`partial` 不能每次直接追加，否则会出现重复文字。前端应按 `segmentId` 和 `revision` 覆盖当前临时句子：

```text
已确认的 final 文字
+ 当前最新 partial 文字
```

临时文字可使用较淡颜色与已确认文字区分；内容较长时文字区内部滚动，保持最新内容可见。前后端都按句子编号维护结果，重复事件覆盖而不追加，已 final 的句子不被迟到的 partial 覆盖；最终按句子顺序组合，保留服务端标点。

录音期间原输入框保留草稿并暂时禁止编辑；识别结束后，仅将已确认文字回填到开始前记录的选区，无选区时在光标处插入，保留原草稿前后文。ASR 文字按纯文本展示，不作为 HTML 执行。

#### 4.5 点击对勾结束识别

语音面板右侧使用对勾按钮，含义是“结束录音并采用最终识别文字”，不是发送问题。点击对勾或达到 60 秒上限时，不能立即断开所有连接，否则最后一小段声音可能还没识别：

1. 前端停止接收新的麦克风输入，向 Worklet 请求排空已处理的尾部音频。
2. 收到尾帧及排空确认后，按序调用 WebSocket 发送；立即停止全部音轨、断开音频节点并关闭本地音频上下文，不在等待云端结果期间继续占用麦克风。排空也需短超时兜底，不能因 Worklet 无响应而一直占用设备。
3. 前端向后端发送 `stop`。
4. 后端排空已入队的音频，再结束 SDK 音频输入流，由 SDK 通知阿里云结束本次识别。
5. 后端等待最终结果和任务完成事件。
6. 后端发送 `complete`。
7. 前端确认本地录音资源已经释放，关闭 WebSocket。
8. 将已确认的最终文字回填原输入框，收起语音面板，恢复编辑和发送；不会自动发送问题。

面板左侧使用 × 按钮，点击后发送 `cancel`，直接终止本次识别、丢弃本次识别文字并恢复原草稿；取消和失败都不能自动发送问题。

等待最终结果期间显示“识别收尾中…”并禁用对勾，保留取消入口；设置超时，不无限等待。超时或失败时关闭连接，保留原草稿，并将本次已确认的 `final` 文字按原选区回填，提示识别未完整完成；`partial` 不作为最终结果回填。没有已确认文字时提示“未识别到文字，请重试”，不改变原草稿。无论正常结束、取消还是失败，都要释放麦克风和上下游连接。

`cancel` 优先于普通收尾，可在授权等待、连接、录音、收尾阶段生效；直接取消 SDK 任务/连接，不阻塞等待 `stop()`。若麦克风权限请求在用户取消后才成功返回，仍需立即停止新返回的全部音轨，不能重新启动录音。前后端关闭动作必须幂等，取消后的迟到结果不得回填。

#### 4.6 确认发送

识别完成后，输入框里就是普通文字：

```text
用户说话 → 面板上方实时出字 → 点击对勾 → 最终文字回填输入框 → 用户修改 → 点击发送
```

点击发送后，才进入文字问答入口；接入第二部分时，由入口统一进行意图分流。后续流程只接收文字，不关心这段文字来自键盘还是语音。

#### 4.7 自有 WebSocket 最小协议

地址固定为 `/api/v1/speech/recognize`；无需 STOMP 或 SockJS。控制信息用 JSON 文本帧，音频用二进制帧；这些是本系统协议，不要求浏览器构造阿里云的 `run-task/finish-task`。

| 方向 | 消息 | 必要内容 |
| --- | --- | --- |
| 浏览器 → 后端 | `start` | `recordingId`、`format:"pcm"`、`sampleRate:16000`、`channels:1`、`bitsPerSample:16` |
| 浏览器 → 后端 | 二进制音频 | 只在收到 ready 后发送，一连接对应一个 recordingId |
| 浏览器 → 后端 | `stop` / `cancel` | `recordingId`；stop 等待最终结果，cancel 丢弃本次结果 |
| 后端 → 浏览器 | `ready` | `recordingId`、`maxDurationMs:60000` |
| 后端 → 浏览器 | `partial` / `final` | `recordingId`、`segmentId`、`revision`、`text` |
| 后端 → 浏览器 | `complete` | `recordingId`、`text`（仅由 final 拼成的本次全文，不包含原草稿） |
| 后端 → 浏览器 | `error` | `recordingId`、稳定错误码、可读提示、`confirmedText`（若有） |

JSON 使用 `type` 区分事件。前端仅接受当前 recordingId 的结果，complete 按最终快照替换本次结果，不再次追加到已显示全文上。`error` 后关闭本次会话，重试由用户重新点击麦克风，不自动重连、重放音频；正常 complete 之前的断线不能当成成功。

### 5. 前端状态设计

两端共用同一套语音核心逻辑，页面只负责按钮和输入框适配。

```text
idle
  → requesting-permission
  → connecting
  → recording
  → finalizing
  → editable
```

异常状态统一回到 `idle`：

```text
permission-denied
connection-error
asr-error
timeout
cancelled
```

交互要求：

- 主网页和悬浮窗使用相同交互：面板上方展示识别文字，下方为“左侧 × 取消／中间音量波形与计时／右侧对勾完成”。
- 连接阶段显示加载动画和“连接中…”，正式录音后才显示动态波形与计时；不显示“请开始说话”。
- 波形根据实际输入音量变化，无声音时保持低幅；不使用始终跳动的假音量动画。
- 右侧对勾仅结束识别并回填，不使用发送箭头，不触发问答请求；左侧 × 取消并恢复原草稿。
- 60 秒从正式录音开始计算，达到上限自动收尾；不设置静音自动停止。
- 录音和等待最终结果期间暂时禁止编辑和发送，避免覆盖识别结果。
- 原问答正在生成时禁用麦克风，暂不允许同时开启语音输入。
- 无识别文字时提示重试，保留原草稿；识别失败保留原草稿和已确认文字，不将临时文字当作最终结果。
- 识别完成后允许修改，不自动发送。
- 路由切换、切换会话、`pagehide`、音轨结束或音频上下文意外暂停时取消识别并释放资源。
- 宿主关闭悬浮窗的联动按此前确认暂不实施：iframe 被移除时按卸载清理；仅 CSS 隐藏 iframe 不能保证内部感知，因此不能承诺“隐藏即停”。现阶段保留 × 手动取消及前后端 60 秒上限；正式接入宿主关闭通知时再补 `postMessage` 联动。
- 使用 `recordingId` 防止旧连接返回的结果写入新一轮输入。

#### 5.1 两端复用和必要运行条件

- 共用不依赖 Vue 的浏览器录音/重采样/结果合并核心与 Worklet，Vue 页面和 `/emb` 只做面板及输入框适配；由构建/静态资源方式分发，不要求 `/emb` 引入 Vue，不维护两套识别算法。
- 当前 Vite `/api` 代理尚未开启 WebSocket 转发，实施时需补 `ws: true`；URL 按页面协议选择 `ws` 或 `wss`，不写死地址，嵌入页默认连接自身同源后端。
- 本机开发可使用 `http://localhost` 或回环地址；普通局域网 IP / 远程域名的 HTTP 页面不能据此保证可调用麦克风及 AudioWorklet。不采用关闭浏览器安全检查的方式绕过。
- 上线时宿主页面和 iframe 页面都需满足安全上下文，浏览器侧使用 WSS。跨域 iframe 需宿主允许 `microphone`，例如 `allow="microphone"`，并确保父页 `Permissions-Policy` 没有禁止；若存在 sandbox，也要核对脚本及来源相关权限。证书申请细节仍不在本文展开。
- 即使暂不支持宿主关闭通知，iframe 的麦克风授权仍是必要条件，不能一并延期。

### 6. 后端模块建议

建议新增以下职责，不与现有文字 RAG 服务混在一起：

```text
SpeechWebSocketConfig
SpeechWebSocketHandler
SpeechSession
AsrProvider
DashScopeAsrProvider
SpeechMessage / SpeechResult
```

- `SpeechWebSocketHandler`：处理浏览器连接、文本指令和二进制音频帧。
- `SpeechSession`：保存一次录音的状态、录音 ID、上游任务和关闭状态。
- `AsrProvider`：定义统一的开始、发送音频、停止、取消方法。
- `DashScopeAsrProvider`：使用官方 Java SDK 实现阿里云调用。
- `SpeechResult`：把厂商结果转换成前端统一的 `partial/final/complete/error`。

ASR 结束后不创建聊天历史、不调用 RAG、不调用数据库，也不提前分类；只有用户点击发送，才进入文字处理流程。

#### 6.1 生命周期与异常保护

- 一次录音独占一个 Provider 实例和云端任务；后端只有一个完成/失败出口，定时器、SDK 回调、取消不能重复完成或重复回填。
- 音频发送串行、SDK 回调快速返回；浏览器结果发送需串行化或使用 Spring 的 `ConcurrentWebSocketSessionDecorator`，不能让多个回调并发写同一 WebSocket。
- 确认收到正常任务结束事件后才发送 complete；不能把普通断线或取消引发的 SDK 流完成回调一律当作识别成功。
- 无权限、无设备、设备占用、格式错误、凭证错误、限流、网络中断、任务失败、等待超时分别提示；认证/计费配置错误不反复自动重试，不把阿里云原始异常和密钥透传浏览器。
- 关闭页面时前端清理只作尽力保证，后端仍靠断线回调、超时和字节上限兜底；应用停止时关闭所有存活任务。

以下为本项目建议的首版保护值，不是阿里云固定配额：

| 限制 | 建议值 / 行为 |
| --- | --- |
| 连接及云端 ready 等待 | 10 秒；不包含用户等待浏览器授权的时间 |
| ready 后无首帧 / 录音中无音频帧 | 各 10 秒；正常思考时仍有静音音频帧，不会因此结束 |
| 录音时长与累计音频 | 60 秒、最多 1,920,000 字节 PCM，超出不再转发 |
| 等待最终结果 | 10 秒；超时保存原草稿与已确认文字，释放云端任务 |
| 音频积压 | 前端监测 `bufferedAmount`，后端使用有界队列，建议最多约 2 秒音频；超过上限报网络慢并结束，不无限缓存 |
| 匿名并发 | Demo 先按总计 5 路、每 IP 2 路配置，且不超过账号实际配额；同一浏览器入口只允许一次录音 |

不加登录，但仍校验握手 Origin 白名单、消息类型、长度、音频格式、并发和频率；缺失 Origin 的调用不默认放行。Origin 校验不是身份认证，公网匿名接口仍有被调用付费的风险，需同时配置账号额度/费用告警。默认不记录原始音频或转写正文，只记录录音 ID、云端请求 ID、耗时、字节量和错误码便于排错。

### 7. 完成标准

- 主网页和悬浮窗都可以点击麦克风。
- 连接就绪并正式录音后才展示录音波形与计时，授权和连接时间不计入 60 秒。
- 面板上方可以实时显示识别文字，无须显示“请开始说话”。
- 临时文字修正时不会重复追加。
- 点击对勾或达到 60 秒上限后，等待最终结果回填输入框，不自动发送；静音不会提前结束。
- 点击 × 取消后恢复原草稿，不保留本次语音文字。
- 可以手动修改最终文字。
- 点击发送后仍按原文字问答流程处理。
- 拒绝权限、断开连接、识别失败、取消录音不会清空原草稿。
- 没有已确认文字时提示重试；识别失败不把临时文字作为最终结果回填。
- 原问答生成期间无法启动麦克风。
- 静音停顿后继续说话仍能实时出字，心跳和空句首不会显示成问题文字。
- 100ms 音频约为 3200 字节，实际重采样正确，最后一句不因过早断开丢失。
- 页面卸载、取消、失败和超时会释放资源；宿主仅隐藏 iframe 的停止联动明确列为延期项，不冒充已支持。
- 真实账号验证 ready 来自任务启动确认；上游认证失败不显示录音状态，异常关闭不伪装 complete。
- 主网页和 iframe 分别验证权限允许/拒绝、取消授权等待、原草稿选区、重复句子、60 秒自动收尾、断网、无语音、长静音及并发限制；本阶段不新增测试代码。

### 8. Demo 落地与展示顺序

1. 先做一次最小 SDK 联调，确认真实账号能启动任务、实时出字、正常结束，且断网/取消不会误报成功；不先开发额外管理功能。

4. 展示时依次演示：正常识别并发送、原草稿上插入语音、× 取消恢复、停顿后续说、60 秒自动收尾。无权限/断网有明确提示，不能靠刷新页面恢复设备。

## 第二部分：文字意图识别与分别回答

### 1. 已有能力与当前不足

- **RAG 已实现：**文档检索、重排、引用来源、答案缓存、历史对话和 SSE 流式返回，可继续复用。
- **三类分流已接入：**统一入口先通过 `IntentRouter` 判断，再进入文档、业务数据、其他分支。
- **保留本地快速路径：**纯算术、整句寒暄和明确回应词不检索；“你好，查考勤人数”不再被问候词截走。
- **支持追问和混合诉求：**类别不明先澄清，业务条件不足继续追问；同轮文档＋数据拆为两个子任务，不增加第四类意图。

### 2. 本期范围

统一支持三类文字输入，分类在后端完成，主网页和悬浮窗共用：

| 类别 | 处理方式 |
| --- | --- |
| `RAG`：文档知识 | 保留现有文档问答能力，按资料回答并引用来源 |
| `BUSINESS_QUERY`：业务数据查询 | 匹配功能说明，按必填条件逐步追问；条件齐全后，未接入的功能明确提示 |
| `OTHER`：其他内容 | 根据内容简短闲聊、说明能力边界、提供简单指引或请用户补充 |

**业务数据库本期不接入、不查库、不生成 SQL、不返回模拟业务结果。** 对话历史仍使用现有 RAG 数据库存储。考勤占位功能先登记必填 `projectName` 演示多轮补条件；日期、统计口径和其他参数待真实接口明确，不猜默认值。

用户登录、角色权限、天气工具、复杂多任务编排不在本部分范围内。

### 3. Agent 设计与流程

采用一个轻量的路由 Agent，不建设三个独立 Agent，也不新增 Agent 框架：

```text
键盘文字 / 已确认的语音文字
              ↓
      后端统一文字入口
              ↓
  IntentRouter：识别类别与处理动作
              ↓
     ┌────────┼────────────┐
     ↓        ↓            ↓
    RAG   BUSINESS_QUERY   OTHER
     ↓        ↓            ↓
 原有文档流程  补条件/未接入提示  按子类型回应
     └────────┴────────────┘
              ↓
      SSE 返回并保存本轮历史
```

无法明确分类时先澄清；“澄清”是处理动作，不新增第四类业务。

- 复用现有文字模型和 Spring AI `ChatClient`，从最近 10 个用户轮次中按关键词、实体、指代、意图和时间选择最多 4 个相关轮次，再结合功能目录返回 `IntentPlan`（1 个任务，或文档＋业务的 2 个任务）。
- 子任务包含类别、动作、完整问题、工具 ID 和已知参数；后端校验白名单。只接收用户明确提供的项目名称，不接受模型生成 SQL、URL 或数据源。
- 保留纯算术和明确纯寒暄的快速路径；包含业务请求的句子不能因出现“你好”“谢谢”而提前直答。
- 分类位于 RAG 检索和答案缓存之前；已经进入 RAG 的问题不再被旧寒暄规则二次截走。
- 解析失败、超时或语义不清时明确提示重试或补充，不默认塞给 RAG，也不放开自由编答。
- 业务分支按功能登记的必填条件追问；“缺勤人员”还缺项目时继续问哪个项目。条件齐全但接口未接入则明确说明，不伪装已经查询。

#### 3.1 后续查询接口接法

- 新增一个服务端 `BusinessQueryTool` 适配器，登记唯一 `id`、名称、用途、示例、参数及追问提示。
- Agent 根据功能说明选择工具和提取已知条件，后端检查缺参后才允许执行。
- 具体查询内容尚未确定，扩展契约不绑定考勤表或其他表；每个真实接口按功能描述、必填参数、返回结构登记，查询数据库由接口内部负责。
- 真实接口由适配器固定配置地址、校验参数、设置连接及读取超时并只读调用；不开放模型直接拼 URL、查库或写 SQL。
- 工具可返回真实结果、需要补充条件、暂未接入或查询失败；没有真实结果不转 RAG 编答，也不把接口失败说成“查无记录”。
- 当前 `attendance_query` 仅为未接入的多轮追问示例，不代表后续接口一定查询考勤或一定需要项目参数；`GET /api/v1/chat/capabilities` 可查看登记说明。

### 4. 回答策略与边界

判断依据是“用户要什么答案、答案应从哪里获取”，不是有没有出现“项目”“考勤”等词。

| 输入示例 | 划分 | 回答方式 |
| --- | --- | --- |
| “农田验收需要哪些资料？” | RAG | 文档回答并引用；没有依据就说明未找到 |
| “考勤制度规定几点打卡？” | RAG | 查制度内容，不当作实时考勤统计 |
| “A 项目今天谁没打卡？” | 业务数据 | 提示考勤查询暂未接入，不编造名单 |
| “查这个项目的考勤人数” | 业务数据 | 上文项目明确则承接；否则追问项目，不猜人数 |
| “考勤” → “缺勤人员” → “江汉一号项目” | 澄清 → 业务数据 | 先区分制度/记录，再补项目，最后提示接口未接入 |
| “报告里记载的参建人数是多少？” | RAG | 查询指定文档记载，不当作数据库实时值 |
| “你吃饭了吗？” | 其他·闲聊 | 简短自然回应，不假装有真实用餐经历 |
| “你能做什么？” | 其他·能力说明 | 只介绍已可用能力，明确数据库查询尚未接入 |
| “明天会下雨吗？” | 其他·实时信息 | 说明未接入天气服务，不编造天气 |
| “天气怎么查？” | 其他·一般指引 | 可简单说明查询方式，不声称已替用户查询 |
| “哦哦哦”“嗯嗯”“好的” | 其他·确认 | 简短回应，不检索 |
| “给你啊放假啊回复” | 其他·不清楚 | 请补充具体问题，不推测想查什么 |
| “解释考勤制度，并查今天谁没打卡” | RAG＋业务数据 | 分段回答制度和查询条件追问，来源仅属于文档段 |
| 明显无关的复杂请求 | 其他·范围提示 | 简短说明当前服务范围，引导提出相关问题 |
| 无意义字符，或“查那个”且无可用上下文 | 无法明确 | 请用户补充具体问题，不强行检索 |

边界规则：

1. 文档问题即使没检索到答案，仍属于 RAG；不能切到通用模型补造专业结论。
2. 业务查询即使未接入接口，仍属于业务数据类；不转给 RAG 代答，不输出真实数据样式的假结果。
3. 其他类不等于开放所有通用问答，只做简短闲聊、能力说明、必要指引和范围提示。
4. “你好，帮我查考勤人数”按实际业务诉求分类，不能被问候词截走。
5. 指代和省略仅在历史明确时承接，不能凭空补齐；没有明确上下文时先追问。
6. 同一句明确包含文档和数据需求，拆为最多两个任务；文档部分先回答，业务部分按缺参追问。补项目后只继续未完成的查询；超过两个或无法拆清时再请用户分开。
7. 用户要求“忽略规则”“伪造人数”等内容不能改变后端分支和能力边界。
8. 混合请求始终按“文档解答”“业务查询”分别说明结果：一个失败仍保留另一个结果；两个都失败则分别解释。未找到文档、缺少条件、功能未接入不冒充调用失败；技术异常明确标注失败分支。文档生成中断时提示已有片段不构成完整结论，不返回该段虚假来源。

### 5. 实施位置

| 位置 / 模块 | 已接入内容 |
| --- | --- |
| 新增 `IntentRouter / IntentPlan / IntentDecision` | 三类识别、多轮追问、双任务和结果校验 |
| 新增 `AssistantDispatchService` | 在后端分流、发 SSE，保证每轮只完成一次 |
| 新增 `BusinessQueryHandler / BusinessQueryTool` | 功能说明目录、条件补齐、未接入占位、后续只读接口适配 |
| `DirectAnswerService` 与其他回答处理 | 保留算术和直答能力，完善其他类子类型；取消关键词决定所有去向的旧逻辑 |
| `ChatController` | 先做基础检查和会话处理，再分类；只有 RAG 分支要求有效知识库及文档范围 |
| `StreamingRagService` | 保留检索、生成、来源及缓存，去掉已由路由负责的重复寒暄判定 |
| 历史与缓存 | 三类回答和澄清都保存历史；路由读取有限上下文。文档缓存只服务 RAG，不缓存业务占位回复 |
| 主网页与悬浮窗输入区 | 放开“无知识库就不能发送”的全局限制；默认状态改为“正在理解问题…”，分类后再显示相应状态 |
| 接口与验证 | 保留现有文字接口及 SSE 形式，不为分类单独更换传输；使用已有测试和临时终端检查验证，不新增测试文件 |

会话保留已有文档范围，但不能因此阻断闲聊或业务数据分支；RAG 分支仍严格校验文档范围，不扩大检索范围。知识库选择与绑定逻辑需兼容先闲聊、后问文档的会话，不能因首次为空而永久无法选择文档。

流式连接由实际回答分支结束；混合请求由调度层统一保存两段回答并只结束一次。文档无匹配或暂时失败，不阻断业务部分追问。对外使用的同步聊天入口复用同一套分类；专用 RAG 查询及文档缓存预热仍保持文档职责。

### 6. 验收标准

- 相同文字无论键盘输入还是语音确认，都进入同一套后端分类。
- RAG 问答的检索、引用、文档范围和缓存不回归。
- 打卡、人数等业务查询正确进入预留分支，不调用数据库、不生成 SQL、不编造结果。
- 问候不遮蔽业务诉求；闲聊不误进 RAG；天气不假装已查询。
- 分类不明确会澄清；缺查询条件继续追问；文档＋业务双任务不丢分支，异常不强行猜测。
- 混合请求覆盖文档成功/业务失败、文档失败/业务成功、两个都失败；各段明确归属，仍正常结束 SSE 并各自保存类别。
- 没有知识库也能闲聊并得到业务查询暂未接入提示；文档分支仍校验知识库。
- 三类回答均能正常结束 SSE、保存历史，不重复写入。
- 本部分实施分类与回答及查询扩展契约，不扩展实际业务数据库查询能力。

### 7. 对话历史与检索范围

#### 7.1 intent 与历史落库

- 继续使用 `kb_chat_session` 和 `kb_chat_message`，不拆分三套历史，不在会话表固定问题类型。
- 消息表新增可空的 `intent VARCHAR(32)`，取值为 `RAG`、`BUSINESS_QUERY`、`OTHER`；不新增 `status`、`turn_id` 等字段。
- 按用户确认，迁移前的全部消息统一回填 `RAG`，包括 USER、ASSISTANT 和已软删会话下的消息；这是一次性历史标记，不重新推断原意图。
- 之前一次性 SQL 位于 `rag/src/main/resources/db/migration/V7__add_chat_message_intent.sql`，已执行，不重复回填。本轮映射实体、保存逻辑并同步新环境建表脚本，不新增数据库字段。
- 新用户消息 `intent` 留空，助手按实际分支写入类别。混合轮保存一次 USER、两条 ASSISTANT，分别标记 `RAG` 和 `BUSINESS_QUERY`，不引入 `MIXED`、`status`、`turn_id`。
- 实时进度继续复用现有 SSE 的 `status/token/done/error`；回答完成后一次性保存问题和回答，不为进度提示增加数据库状态字段。
- 匿名访问者共享查看和管理会话；数据库完整保留历史。模型先读取最近 10 个用户轮次作为候选，再选择最多 4 个相关轮次及其全部子回答，不把混合轮误当“两条消息”。
- 相关记忆不是按 `intent` 简单过滤：相同意图但主题无关的轮次可以排除；“这个项目”“然后”“继续”等短指代优先检查最近轮次；项目、人员、日期等实体一致时提高关联度。当前问题明确切换主题时，旧主题降权。

#### 7.2 非 RAG 过滤检索字段

`kb_ids`、`doc_id` 是现有会话级检索范围，不是意图或业务数据库编号。无范围时分别使用 `[]` 和 `NULL`；`doc_id` 为 BIGINT，不能存数组。

| 情况 | kb_ids / doc_id 处理 |
| --- | --- |
| 新建非 RAG 会话 | 过滤请求附带的知识库和文档，保存 `kb_ids=[]`、`doc_id=NULL` |
| 已有会话中出现非 RAG 问题 | 本轮不使用、不校验知识库和文档；不清空已有会话范围，避免影响后续文档追问 |
| 进入 RAG 分支 | 使用已绑定范围；若会话原先为空，接收页面选定或配置的有效默认知识库并绑定，再校验、检索 |

- 分类前只做文字、会话等基础检查，不因无知识库或文档失效拦截非 RAG 问题。
- 只有 RAG 分支检查知识库有效性、文档归属和可用状态；没有有效范围时提示选择或配置知识库。
- 非 RAG 回复的文档 `sources` 保存 `[]`，不调用检索，也不返回虚构的引用。
- 以上过滤与绑定已接入，不批量清空既有会话范围。普通 `POST /api/v1/chat` 和 SSE 入口共享路由；文档缓存预热保持 RAG 专用。
